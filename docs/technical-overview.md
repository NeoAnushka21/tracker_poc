## 1. Tech stack

| Layer | Choice |
|---|---|
| Frontend | React 19, TypeScript, Vite. No UI or chart library: charts are hand-rolled SVG (`charts.tsx`). |
| Styling | One `styles.css` with CSS custom-property tokens (colours, `--radius` 22px / `--radius-sm` 14px, `--shadow-card` (wide, faint), `--accent-grad` (text-safe: forest green, readable white text in light / dark text in dark), `--brand-grad` (the logo's green → yellow-green → amber, decoration only: the active-tab underline), `--glass`, and the motion curves `--ease-out` for fills and `--ease-spring` for reveals). Light and dark via `prefers-color-scheme` and `data-theme`. **Responsive:** one layout for phones and tablets (a `max-width: 860px` block tightens spacing and grids), and from `min-width: 1024px` a "wide screens" block at the end of `styles.css` adds columns: Home (summary tile + `.home-side` with the water tile and streaks), Dashboard (`.dash-cols`: `.dash-summary` with the macro, micronutrient and water tiles + `.dash-meals`), Analysis (`.analysis-charts`, 2 columns, CSS `order` pairs the cards), Explore (`.explore-grid`, auto-fill tiles). My Foods is a one-column list at every width. Content is capped by `--content-max` (1200px), and `--edge` gives the top bar, tabs and pages the same outer edge. Chat bubbles cap at 780px for line length. |
| Font | Plus Jakarta Sans (variable), self-hosted via `@fontsource-variable/plus-jakarta-sans` (no Google Fonts request) |
| Voice | Browser Web Speech API (`useSpeechToText.ts`), on-device or browser-vendor; no server audio. |
| Barcode scanner | In the browser, loaded on first use (`scan.ts`): the browser's own **BarcodeDetector** where there is one (Chrome on Android), else **zxing-wasm** (MIT, its `.wasm` bundled in `/assets`, no CDN), for EAN/UPC barcodes in camera frames or photos. Barcode only (owner, 2026-10-01): reading the front of a pack failed on real photos. Photos never leave the device. |
| Backend | Python 3.12+ (developed on 3.14), FastAPI, Uvicorn |
| ORM / DB | SQLAlchemy 2.x. Development: SQLite (`backend/macro_tracker.db`). Production: Postgres on Neon via `psycopg` 3 (`db.make_engine` rewrites `postgres://` URLs to the psycopg driver and pings pooled connections, since Neon suspends idle databases) |
| Hosting | One free Render web service (`render.yaml`, Singapore): builds the React app, and FastAPI serves it plus `/api`. See [deployment.md](deployment.md). |
| Auth | Email + password (**Argon2id** via `argon2-cffi`: 19 MiB, 2 passes, 1 lane, OWASP's minimum; older scrypt hashes still verify and are re-hashed on the next successful login; an unknown email does the same hashing work as a wrong password, so timing doesn't reveal which emails exist) or **Continue with Google** (Google Identity Services button; `app/google_auth.py` verifies the RS256 ID token with PyJWT's `crypto` extra and Google's JWKS). Either way, a PyJWT session token in an httpOnly cookie (`SESSION_DAYS`, default 14) carrying the user's `session_version` (`sv`); `deps.current_user` rejects a token whose version is out of date, so bumping it ends every session (password change: other devices; Log out of all devices: all). Tokens without `sv` count as 0. |
| LLM | `openai` SDK against any OpenAI-compatible host (default Groq `openai/gpt-oss-120b`), or the `anthropic` SDK |
| Tests | pytest + FastAPI TestClient, with a `FakeProvider` in place of the LLM (no key or network needed) |

## 3. Backend services

| Module | Responsibility |
|---|---|
| `services/actions.py` | Pending-action lifecycle: `confirm_action` (the only writer for LLM proposals: create, edit, delete, move, copy, water, save_recipe), `reject_action`, `supersede_older`, `expire_stale` (24 h). `from_dashboard(a)` marks estimates from the Dashboard's Add food (`payload.origin == "dashboard"`): `open_actions` (what the chat and the model see) leaves them out, `supersede_older` never replaces them, and their confirm/reject events say "On the dashboard…". |
| `services/logs.py` | Totals, `daily_summary` (macros, micros, water, targets), `logs_by_day`, current targets and weight |
| `services/preferences.py` | Optional "about you" answers (`user_preferences`). `options()` (choices from config: `DIET_TYPES`, `ALLERGENS` with keywords, `PACE_OPTIONS`, `TRAINING_TYPES`, `HEALTH_CONDITIONS`, `PREGNANCY_STATES`), `check` (choices only; meal times HH:MM, in order, ≥2 h apart; pregnancy only for a female profile; health answers need `health_consent`), `save` (sets or clears `health_consent_at`), `skip`. Every answer is used: `target_options` (pace; `no_deficit` while pregnant/breastfeeding) → `nutrition.calculate_targets`; `meal_times` → `timeutil.meal_windows` / `infer_meal_type` / `resolve_meal_type` (tools, confirm) and the Dashboard's default meal time (`entries.eaten_at_for_meal`); `prompt_lines` → `about_user` in MacBro's context; `allergen_note` → a "Heads-up" on fast-path and general-list cards. |
| `services/places.py` | Countries and regions from `app/data/countries.json` (built by `scripts/build_countries.py` from the `country-region-data` npm package, MIT, pinned to 4.1.0; licence in `countries.LICENSE.txt`). `countries()` (only `config.SUPPORTED_COUNTRIES`, `["IN"]` for now; the data file keeps all 249, so adding a country is adding its code), `check(country, region)` (refuses countries not offered) (country = ISO 3166-1 alpha-2 code, case-insensitive; region must be one of that country's names, or empty; else `ValueError`), `country_name`. Regions are stored by name because 13 small territories have regions without codes. |
| `services/general_foods.py` | The **general food list**: loads `app/data/general_foods.json` once (`_load`: entries by id, raw/cooked groups by base name, an alias index like `library_index`). `find(typed)` → `Match(base, entry, options)`: whole names first ("boiled egg", "dried figs"), then with state words removed; `entry is None` with options `["raw", "cooked"]` means **ask**. `state_in` / `strip_state` (raw, uncooked, dry → raw; cooked, boiled, steamed, grilled, roasted, baked → cooked). `grams_for` (g/ml, piece/slice, and USDA household measures cup/tbsp/tsp, else the model's `unit_weight_g`), `resolve_item` (a `general_id` item → nutrients and micronutrients computed in code, `source = "general"`), `context_lines` (list foods named in the message for the AI). To change the list: edit `scripts/general_foods_spec.py`, download the USDA SR Legacy CSV, run `scripts/build_general_foods.py <folder>`; the build fails on a missing USDA name (with suggestions), a raw/cooked pair missing a half, or two foods sharing a typed name. |
| `services/foods.py` | Food library: unit normalisation, `scale_factor`, `measurable_units` (units a saved food can be logged in; `units` in the food JSON), `library_index` / `match_saved` (typed name → saved food, plural-tolerant, ambiguous names left out; shared with the fast path), **typos in plain Python:** `edit_distance` (letters added, dropped, changed or swapped, with an early stop), `typo_limit` (0 under 5 letters, 1 from 5, 2 from 9), `closest_saved` (exact match, else the one saved food within the limit; none if two are), and `library_context` also lists foods whose words are a typo away from the message, `resolve_library_item`, `upsert_estimate` (teach on confirm, never overwrite user-edited foods), `upsert_general` (a confirmed general-list food → My Foods with the list's exact per-100 g numbers and piece weight, `source = "general"`; an existing food of that name is kept), `learn_item` (picks between the two), `closest_saved(..., strict=True)` for the big general list (typos only from 6 letters, first letter must match: "idlis" isn't "imli"), `compute_recipe`, `save_recipe` Branded foods: `library_index` also keys "brand name" and "name brand"; `apply_label` (label values in, `source = "label"`, `label_checked`, `off_code`; piece weight kept); `correct_past_logs` (recomputes non-deleted `log_entry_items` with this `user_food_id`; items in an unconvertible unit are skipped). `upsert_estimate` never overwrites `recipe`, `user` or `label` foods; `library_context` marks label foods `| label |`. `typed_ingredient` (+ Add → Recipe): a typed ingredient → an item with nutrients, from My Foods (picked `food_id`, or `match_saved`) else the general list (`general_foods.find` / `resolve_item`); `FoodError` with a user-facing message for an unknown food, raw/cooked not said, or a unit the food can't be measured in. |
| `services/labels.py` | Pack labels for branded foods from **Open Food Facts** (`world.openfoodfacts.org`, ODbL data, no key). `search(text)`: full-text search (`cgi/search.pl`), or a barcode (8–14 digits) looked up directly; only complete labels (kcal, protein, carbs, fat), sold-in-India first, up to 8. `get_label(code)`: one product by barcode (`/api/v2/product/{code}.json`). `product_to_label`: per 100 g/ml (ml when the pack size is in ml/l), kcal from kJ ÷ 4.184 when missing, minerals and vitamins from grams to mg/mcg, `serving_quantity` → `grams_per_serving`. Sends only the search words or barcode, with `User-Agent: Tandurust/1.0 (PUBLIC_APP_URL)`; 12 s timeout (callers can pass a shorter one); `LabelLookupError` on failure. Labels also carry `brands` (every brand listed) for matching. |
| `services/label_match.py` | **Pack labels on chat cards** (2026-10-01). `attach(db, user, items, scanned_code)`, called by `tools._with_labels` from `propose_entry` / `propose_edit` (not on Dashboard estimates): every branded AI estimate (`source = estimate`, `brand_name` set) gets `label_match = {status, options, query, how, picked}`. `search_many` checks `label_cache` (fresh for `LABEL_CACHE_DAYS`), fetches the rest side by side (thread pool, `LABEL_AUTO_TIMEOUT_S` = 5 s each, stragglers dropped) and stores answers with an insert-or-update that's safe for two users at once. `rank` keeps products whose brand matches (typos allowed via `foods.edit_distance`) and that share a name word, drops the same label in another pack size, orders by brand + name coverage + sold in India − extra words, and says `sure` only when the top one has every name word, at most one extra word, is sold in India, and no other full match has numbers more than 5% apart; else `choose`; `none` / `unavailable` otherwise. `label_item` puts the label's numbers on the item for its amount: grams, the label's serving weight, or the AI's `unit_weight_g` (`weight_estimated`); it keeps the AI's numbers in `estimate` and the label in `label`. `pick(action, i, code)`: only a code among the stored options (the browser never sends numbers); `None` restores the estimate (`declined`). `search_again` for **Find the label**. A barcode sent with the message, or a pick on the card being replaced (`_previous_picks` from open cards), comes ready on the new card (`how` barcode / picked). On confirm, `foods.learn_item` → `upsert_label_item`: the saved food with that barcode, or name + brand, else a new one, gets `apply_label` (source `label`, `label_checked`), plus the AI's piece weight when logged in pieces. |
| `services/entries.py` | Direct item operations: `add_saved_food` (a saved food scaled in code, new entry in the meal), `eaten_at_for_meal` (the meal's latest time that day, else `MEAL_DEFAULT_TIMES`, capped at now), `transfer_items` (move/copy), `set_item_quantity`, `delete_item` (soft-deletes an empty entry), `record_event` (chat note so the model knows) |
| `services/water.py` | Water target (35 ml/kg + activity extra), add/delete, daily summary |
| `services/analysis.py` | `range_summary` for 7/14/30 days, `on_target` (±10% kcal, ≥90% protein; Analysis only); `streaks` for Home: meal logging and **protein** (`protein_hit`: protein ≥ `PROTEIN_STREAK_MIN_SHARE`, 85%, of that day's target; calories ignored), 365-day window; today only counts once it qualifies, so it never breaks a streak. Response keys: `logging`, `protein`, `last_7_days[].protein_hit`, `rule.min_protein_pct` |
| `services/body.py` | `bmi()` (WHO categories on the displayed one-decimal value) and `body_fat_navy()` (US Navy equations, Hodgdon & Beckett 1984; men: height, neck, waist; women: + hips). Returns `missing` or `implausible` (non-positive log argument, or outside `BODY_FAT_PLAUSIBLE`) instead of a number; `routers/profile.body_profile` adds a warning when the inputs are more than 30 days apart. |
| `services/progress.py` | Card after a confirm, for the day the change landed on (`routers/actions._action_day`: `drank_at_utc` / `eaten_at_utc` / `to_date`, else today). Water confirms get `build_water_progress` (`focus: "water"`: litres, % of goal, hydration line); food changes get `build_progress` (`focus: "macros"`: calories, macro %, motivational line). Both carry `date` and `is_today`. |
| `services/micros.py` | Clean, scale and total the micronutrient JSON |
| `services/cancel.py` | In-memory registry for the Stop button: `start`, `raise_if_cancelled`, `finish_or_cancelled` (atomic check before commit), `cancel` |
| `services/allowance.py` | Daily AI allowance: `status` (limit, used, remaining, `resets_at` = next local midnight), `check` (raises `AllowanceExceeded` before any model call), `record` (one `ai_requests` row, committed with the reply, so failed or stopped requests don't count). Counted: AI-answered chat messages (`llm/chat.py`, after the fast paths) and Dashboard estimates (`routers/entries.add_food`, new foods only). |
| `services/ratelimit.py` | In-memory sliding windows for sign-in and the waitlist form (`check_waitlist`: `WAITLIST_REQUESTS_PER_IP`, 5 per `WAITLIST_REQUEST_WINDOW_S`, an hour, per address): wrong passwords per email (`LOGIN_FAILURES_PER_EMAIL` in `LOGIN_FAILURE_WINDOW_S`, cleared on success) and login/register/Google requests per address (`AUTH_REQUESTS_PER_IP` in `AUTH_REQUEST_WINDOW_S`; address = first `X-Forwarded-For` entry, which a client can fake only to dodge its own limit). 429 with a wait time. A restart clears them. |
| `services/export.py` | `export_user_data`: every row the user owns (account, weights, targets, measurements, food log with items, water, My Foods with recipe ingredients, chat, proposals, AI requests and model calls, and admin views of the account), with the password hash and Google id left out. |
| `services/password_reset.py` | Forgot password: `create_link` (32-byte token, only its SHA-256 stored, `PASSWORD_RESET_MINUTES`, older open links retired; link = `PUBLIC_APP_URL/reset-password#token=…`, never the request's Host), `use_link` (once, unexpired; sets the password, bumps `session_version`) |
| `services/email.py` | Brevo HTTP API (`BREVO_API_KEY`, `EMAIL_FROM`); `enabled()` is true when configured, or in development (then the email is logged instead of sent). Sent as a background task after the response. |
| `services/waitlist.py` | Invite-only sign-up (2026-10-01). `may_create_account(email)` (always true when `JOIN_MODE=open`; else the email must have an approved `waitlist` row), `require_invite` (403 with `NOT_INVITED`, called by `auth.register` and, for a new account only, `auth.google_login` before the consent step), `signup_link` (`LAUNCHER_ORIGIN or PUBLIC_APP_URL` + `/#signup`), `alert_text` / `invite_text` (plain-text emails). |
| `services/totp.py` | Admin two-step sign-in (TOTP, `pyotp`): secret encrypted with a key derived from `SECRET_KEY` (Fernet), QR as an SVG data URI (`segno`), ±1 step clock drift, each time step accepted once (`users.totp_last_step`). `scripts/reset_admin_2fa.py` turns it off for a lost phone. |
| `services/accounts.py` | `delete_user_and_data`: deletes the user's `waitlist` row (matched by email) and the user row; the database's ON DELETE CASCADE removes every row they own, and SET NULL keeps and unlinks the admin audit trail and model-usage rows (migration 0003) |

## 4. HTTP API

All endpoints are JSON under `/api`, authenticated by the session cookie. Every query is scoped to the current user.

**Request ids and errors** (`app/observability.py`): every response has `X-Request-ID`; app log lines (`tandurust.*`, `macbro.*`, INFO) carry it. Sentry settings: `send_default_pii=False`, `max_request_body_size="never"`, `include_local_variables=False`, no tracing.

**Security headers** (`main.security_headers` middleware, every response): a Content-Security-Policy that allows only our own files plus Google's sign-in origins (`https://accounts.google.com/gsi/client`, `/gsi/`, `/gsi/style`, as Google documents), no inline scripts (the theme script is `public/theme-init.js` for this), `'unsafe-inline'` for styles only (React style attributes), `frame-ancestors 'none'`, `object-src 'none'`; `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (microphone and camera for our own pages only), `script-src 'wasm-unsafe-eval'` (compiling WebAssembly for the pack scanner, our own files; it doesn't allow JavaScript `eval`), `Cross-Origin-Opener-Policy: same-origin-allow-popups` (Google's sign-in popup), and HSTS (one year) only over HTTPS. The Vite dev server doesn't send them, so check CSP changes on the built app served by the backend (`http://localhost:8000`). A new external script, frame or API the page calls must be added to `CONTENT_SECURITY_POLICY`.

`GET` (and `HEAD`, for uptime monitors that keep the free service awake) `/api/health` returns `{"ok": true}` without touching the database, with `Access-Control-Allow-Origin: *` and `Cache-Control: no-store` so the welcome page on the static site (another origin) can poll it.

**Database conventions (migration 0003, 2026-09-30).** `db.Base` has a naming convention (`ix_`, `uq_`, `fk_<table>_<column>_<referred>`, `pk_`), so every constraint has a predictable name. Timestamps use `db.UTCDateTime`: `timestamptz` in Postgres, naive UTC in Python (existing code unchanged). Every foreign key has an ON DELETE rule: CASCADE from `users` (and entries → items, recipes → ingredients), SET NULL for `llm_usage.user_id`, `admin_audit.target_user_id`, item → saved food, and pending-action / chat links to entries. Per-user tables have a composite index `(user_id, <date or status>)` instead of a single `user_id` index. On SQLite `app/migrate.py` runs migrations with foreign-key checks off (table rebuilds would otherwise cascade) and runs `PRAGMA foreign_key_check` before committing. Public UUIDs are only on users: entries, items, cards and foods keep integer ids because the model refers to them in its context (short ids keep prompts small and accurate), and every endpoint checks ownership.

**Migrations (Alembic, since 2026-09-29).** `app/migrate.py` runs at startup: an empty database gets every migration (`0001` is the baseline of the schema on 2026-09-29); a database from before Alembic (tables but no `alembic_version`, e.g. Neon) is first brought to the baseline the old way (missing tables, nullable columns via `db.add_missing_columns`, missing indexes), stamped `0001`, then upgraded; otherwise pending migrations run. To change the schema: edit `app/models.py`, then in `backend/` run `.venv\Scripts\alembic revision --autogenerate -m "what changed"`, review the new file in `migrations/versions/` (autogenerate misses renames and data changes), and commit it with the model change. `tests/test_migrations.py` fails if the models and migrations disagree. `data_migrations.run_all()` still handles one-off data fixes and creates the admin account from `ADMIN_INITIAL_PASSWORD` if it's missing.

|---|---|
| `router.py` | Rule-based **routing**: intent (`query`, `edit`, `log`, `full`) and tier (`small` / `large`), plus the tools and prompt sections each intent gets. Leans towards `large` when unsure (vague dishes, 3+ foods, several meals, no amounts, recipes, feedback on a card, long messages). |
| `pool.py` | **Model pool**: models per tier from config (+ optional `llm_pool.json` providers). | `fastpath.py` | **No-LLM replies** for common messages. `_state_answer` runs first: if MacBro's last reply asked raw or cooked (`data.ask_state = {text, items}` on that message), a short answer ("cooked", typos ok, or "chicken raw, rice cooked") re-runs the original message with the states filled in. | Tool | Kind | Effect |
|---|---|---|
| `get_food` | read | Look up the user's library by name |

| `get_daily_summary` | read | Totals against targets for a day |

| `propose_edit` | propose | Replace an entry's items → `edit` |
| `propose_delete` | propose | → `delete` |
| `propose_move` | propose | Move or copy items to another meal/date → `move` / `copy` |
| `propose_recipe` | propose | → `save_recipe` |
| `propose_water` | propose | → `water` |

**Guards in code (not just the prompt)**

- **Energy balance:** each item's kcal must be within ±25% of 4·P + 4·C + 9·F. Alcohol is exempt. Otherwise the tool returns an error and the model must recalculate.
- **Quantity cleanup:** strips a leading quantity duplicated in the name ("50 g rice" at 50 g becomes "rice").
- **False-claim nudge:** a reply that says "logged/saved" without a proposal is sent back once. Any remaining "Logged…" wording becomes "Here's…".
- **Missed-water nudge:** if the message mentions water but no `propose_water` was made.
- **Move vs delete:** a move request must use `propose_move`, never delete + create.
- **Tool allow-list:** only the tools offered for the routed intent run; a call to any other tool name is returned to the model as an error (`chat._run_tool_loop`). Corrections like "the chicken was 150g" route to the edit tools (`router._EDIT`: `was/were + number`).
- **One call per meal:** proposals carry the reply in `note`, which ends the turn.

**Failure handling:** a provider exception returns HTTP 503 with `LLM_UNAVAILABLE_MESSAGE` ("MacBro's servers are temporarily down…"). `SHOW_LLM_ERRORS=true` shows the raw error in development.

**Tool schemas are enforced by the host.** Groq validates each tool call against its JSON schema and rejects the whole reply on a mismatch ("expected object, but got null"). A field the prompt allows to be null must be nullable in the schema too (e.g. an item's `micronutrients`, null for saved foods). `test_routing` checks this for micronutrients.

| `FRONTEND_DIST` | Built frontend folder served by the backend (default `frontend/dist`) |
| `VITE_APP_URL` (frontend build) | Only for the static site's build: the app's address the welcome page wakes and sends people to (`render.yaml`); empty = same origin (the app's own `/welcome`, and `/welcome` in dev). |
| `TARGET_DATABASE_URL`, `SOURCE_DATABASE_URL` | Only for `scripts/copy_to_postgres.py` (target Neon; source defaults to the local SQLite file) |
| `TEST_DATABASE_URL` | Only for tests: run the suite on a throwaway Postgres |

Production values live in the Render dashboard (`render.yaml` declares them; secrets are `sync: false` or generated), never in the repo.

Domain constants (`BODY_PARTS` with how-to-measure tips, `BMI_CATEGORIES`, `BODY_FAT_PLAUSIBLE`, meal windows, goal multipliers, activity factors, water, fiber, micronutrient reference values, adherence thresholds, consent text and version) are in `backend/app/config.py`.

## 11. Known limitations and next steps

- A single process (one Render instance). The Stop-button registry, the sign-in attempt limits and the model pool's cooldowns are in memory, so multiple instances would need Redis or the database; a restart (e.g. Render waking from sleep) forgets cooldowns.
- The free-tier LLM quota caps daily usage. Phases 1–3 of [llm-routing-strategy.md](llm-routing-strategy.md) are in (fast paths, routing, pool); a second provider (phase 4) and the evaluation run (phase 5) need decisions and accounts.
- Deferred: OTP email verification, data export, a scheduled cleanup of stale proposals. Deployment is set up (Render + Neon, [deployment.md](deployment.md)); an uptime pinger and a custom domain are open decisions.
