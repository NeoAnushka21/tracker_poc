The deep-dive sections after that cover requests, authentication, the database schema, users, concurrency and failure modes.

Five rules that explain most of the design

Read these first; every diagram below is a consequence of one of them.

1. The LLM only proposes

The model can create a pending action (a card), never a row in the food log. Only services/actions.py → confirm_action writes, and only after the user presses Looks good.

2. Numbers come from code when possible

Saved foods (My Foods) and the built-in USDA list are scaled in Python. The model's arithmetic is checked (4·P + 4·C + 9·F within ±25%).

3. Direct clicks skip the LLM

Meals-tab edits, water buttons, My Foods and dashboards hit the database straight through REST endpoints.

4. Free and open-source

Open-weight models only (Apache-2.0 / MIT, enforced in code) on Groq's free tier; free Render, Neon, Brevo, UptimeRobot, Sentry tiers.

5. Degrade gracefully

If every model is down, chat says "MacBro's servers are temporarily down" (HTTP 503); everything that isn't chat keeps working.

2 · What happens when a user types to MacBro Main diagram

Example: the user types "150g chicken and a cup of rice for lunch" and presses Send. Most messages never reach the LLM at all (fast paths). When they do, the model works through a tool loop: it can read data and propose a change, and the proposal comes back as a card that the user must confirm.

MacBro pipeline: browser → FastAPI → fast path or router → tool loop → model pool → Groq → tools/guards → pending card → confirm

Why prompt injection can't write data: even if a message tricks the model, the most it can do is create a card. The tool handlers only touch the current user's rows, tools outside the routed allow-list are refused, and the database write needs a human button press (tests/test_llm_hardening.py).

Token budget (why routing and fast paths exist)

Groq's free tier gives each model about 200K tokens/day, shared by every user. A full call used to be ~4.4K tokens (≈40 calls a day). Sending only the routed tools, a slimmer prompt and only the saved foods named in the message cuts a call by 25–87%; fast-path messages cost nothing. Each user also has a daily allowance of 20 AI-answered messages (AI_DAILY_MESSAGE_LIMIT); failed calls and instant replies don't count. Everything is logged in llm_usage and shown in the admin AI usage panel.

Authentication: how it works and why it fails

Three ways in: email + password, Continue with Google, and a separate admin login with two-step codes. All three end the same way: the backend sets its own session cookie.

Session model

  • Token: a PyJWT token signed with SECRET_KEY, holding the internal user id and sv (session version). Stored in an httpOnly, SameSite cookie (Secure over HTTPS), so page JavaScript can't read it. Users: 14 days; admins: 12 hours.
  • Log out everywhere / password change: bump users.session_version; every older token now fails the sv check.
  • Google: no client secret, no OAuth code flow; just verifying Google's signed ID token. Google accounts are linked to an existing password account only after the user confirms.
  • Passwords: Argon2id (OWASP settings); old scrypt hashes upgrade on next login. Forgot password = one-time link via Brevo (only its SHA-256 stored, 30 min).

Why a sign-in fails

ResponseCause
401No cookie, expired JWT, bad signature (e.g. SECRET_KEY changed → everyone is signed out), or sv out of date (logged out everywhere / password changed). Wrong password. Bad Google token (signature, audience, issuer, expiry, unverified email). Admin login without a valid two-step code.
403An admin email used on the normal login, register or Google. Invite-only mode and the email isn't approved on the waitlist (NOT_INVITED). A user calling an admin endpoint. Consent outdated / not onboarded (the UI shows the consent gate or onboarding).
409This Google account's email is already linked to a different Google account.
429Too many wrong passwords for one email (10 / 15 min) or too many auth requests from one IP (60 / 10 min). In memory, so a restart clears them.
503Google sign-in not configured (GOOGLE_CLIENT_ID empty) or email not configured for Forgot password.
Google button missingGOOGLE_CLIENT_ID empty, or the page's origin isn't in the client's authorised JavaScript origins (locally use localhost:5173, not tandurust.localhost).

Integrity: every foreign key has an ON DELETE rule. Deleting a user cascades through everything they own; llm_usage and admin_audit rows are kept but unlinked (SET NULL). Timestamps are timestamptz (UTC). Per-user tables have composite indexes on (user_id, date) or (user_id, status).

How users are managed and kept apart

Multi-tenant by user_id

One shared database. Every query is filtered by the signed-in user's id, taken from the cookie, never from the request body. Other users' ids return 404.

Signup states

Account → consent (versioned) → onboarding (18+, country, body, goal) → optional About you → first-run guide → app. GET /api/auth/me tells the UI which gate to show.

Invite-only mode

JOIN_MODE=waitlist: visitors join a waitlist; the admin approves; Brevo emails an invitation; only then can that email register or use Google.

Admins

Fixed emails (ADMIN_EMAILS), separate login with TOTP. Read-only view of users, every view audited. Admins are hidden from the user list.

Privacy rights

Download my data (every row, secrets excluded) and full account deletion (DB cascade + waitlist row).

Fair use

Per-user daily AI allowance (20). Sign-in rate limits per email and per IP. Waitlist form 5/hour per IP with a honeypot.
